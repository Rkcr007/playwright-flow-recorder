# Converting a recording with any AI assistant

The recorder is agent-agnostic. If you use **Claude Code**, install the packaged skill
(`npx playwright-flow-recorder init` puts it in `.claude/skills/record-flow/`) and just
type `/record-flow` — it drives the whole loop, including live-following your clicks.

If you use Cursor, Copilot Chat, Windsurf, Aider, ChatGPT, or anything else, paste the
prompt below. It encodes the parts that actually determine output quality: reuse-first
reconciliation, honest handling of assertions, and a human review gate.

---

## The prompt

> You are converting a recorded browser walkthrough into an automated test for THIS repository.
>
> **Inputs**
> 1. `<RECORDING>` — a JSONL event stream. One JSON object per line. Read `docs/EVENT-FORMAT.md` if the shape is unclear.
> 2. `<REUSE_INDEX>` — the project's existing step definitions and locators (generated by `npx playwright-flow-recorder index`).
> 3. `<CONVENTIONS>` — the `conventions` block from `flow-recorder.config.json`: where specs, steps, locators and fixtures live, the standard scenario opener, the dry-run command, and mandatory tags.
>
> **Rules — follow all of them**
>
> 1. **Only convert what is inside a segment.** Interaction events exist only between a `recording-start` and a `recording-stop` marker. Everything before ⏺ was login and navigation: express that with the project's EXISTING opener + navigation steps, inferred from the `url` on the `recording-start` marker. Never generate steps for pre-⏺ actions.
> 2. **Reuse before you write.** For every action, search `<REUSE_INDEX>` for a step pattern that already covers it, and for every element, a locator key that already targets it. Only author something new when nothing fits. A duplicate of an existing step is a defect, not a convenience.
> 3. **Show your work before creating files.** Output a reconciliation report first: the draft scenario with every line marked `[existing]` or `[NEW]`, then the list of new step definitions, then locator changes split into *additions* and *modifications* (old → new). Wait for approval on the NEW and modified items.
> 4. **Pick stable selectors.** Each element carries several `candidates`. Prefer, in order: `data-testid`-style attribute → stable `id` → `aria-label` → `placeholder`/`name` → text XPath → `css-path`. Flag any element whose only candidates are text or css-path as fragile. For text XPaths use `normalize-space()`, and prefer `contains`/`starts-with` for amounts and currency (rendered pages often contain non-breaking spaces where the source has normal ones).
> 5. **Honour assertion predicates exactly.** Every `assert` event carries a `predicate`: `text`, `visible`, `enabled`, `disabled`, `editable`, `readonly`, `checked`, `row`, `absent-later`. Generate the assertion that matches. Never downgrade `visible`/`enabled`/`checked` into a text check. Every `note` event that reads like a verification also becomes an assertion.
> 6. **Make it re-runnable.** Classify every literal value in the stream as: *literal* (the exact value is the point), *fixture* (resolve it from the project's test-data files), *generated* (must be unique per run), or *precondition* (the entity won't exist on a clean run and needs seeding first). Then answer explicitly: "will this pass twice in a row on a clean account?" If the flow consumes state, add the setup steps.
> 7. **Bind dynamic values.** If an asserted string contains something typed earlier in the same segment, bind the assertion to that input rather than hardcoding the value.
> 8. **Never invent a secret.** Values recorded as `***masked***` are resolved from the project's fixture files by reference. Do not guess them, do not ask for them in chat, and do not put them in the spec.
> 9. **Prefer response waits over sleeps.** `net` events show which XHR/fetch calls the flow triggered. Use them to wait on the real signal instead of a fixed delay.
> 10. **Tag it and gate it.** Add every tag in `<CONVENTIONS>.tags` (typically `@recorded @wip`) plus the relevant suite tag. `@wip` stays until a human reviews the scenario — **a passing dry-run does not remove it.**
> 11. **Report honestly.** After dry-running with `<CONVENTIONS>.dryRunCommand`, state exactly which scenarios pass and which don't, with the real error. Do not describe a failing test as done.
>
> **Output order**
> 1. Reconciliation report (wait for approval)
> 2. The spec/feature file content
> 3. Any new step definitions
> 4. Any locator additions/modifications
> 5. The dry-run command to verify

## Wiring it up

```bash
# 1. Build the reuse index, scoped to the domain you recorded
npx playwright-flow-recorder index --steps orders

# 2. Find the recording
cat .flow-recorder/recordings/latest.txt
```

Then hand your assistant the three inputs:

| Placeholder | Where it comes from |
|---|---|
| `<RECORDING>` | the path in `latest.txt` |
| `<REUSE_INDEX>` | `.flow-recorder/step-index.json` |
| `<CONVENTIONS>` | the `conventions` block of `flow-recorder.config.json` |

For a large index, don't paste the whole file — most assistants handle it better if you
let them grep it. The index is deliberately plain JSON for that reason.

## Driving the queue (optional)

If you want the on-page widget to show live conversion progress, your assistant can
write the ack sidecar next to the recording:

```jsonc
// <recording>.jsonl.ack
{
  "items": {
    "q1": { "status": "done",    "message": "added to orders.feature" },
    "q2": { "status": "working", "message": "reconciling steps" }
  },
  "current": "q2"
}
```

The recorder polls this and merges it with `<recording>.jsonl.queue.json` (which it owns),
so the widget reads `⏳ scenario-2 (reconciling steps) · ✓ 1`. Two files, two writers, no
locking. Statuses are `queued` → `working` → `done` | `error`.

This is entirely optional — conversion works fine without it; you just don't get the
in-browser progress readout.
